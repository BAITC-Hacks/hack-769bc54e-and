# SCOPE.md — границы решения и известные ограничения

Задача #79-lite, команда AND. Разбор Задачи — в `CLAUDE.md`, задачи — в `TASKS.md`.

Ответов от организаторов не будет: работаем по тексту ТЗ и двум присланным файлам.
Поэтому каждая двусмысленность закрыта **решением**, а не вопросом. Сами решения —
в README, раздел «Принятые допущения»: эксперту важнее увидеть осознанный выбор,
чем угадывать, что мы имели в виду. Здесь — что решение делает и чего не делает.

## Что решение делает

| Возможность | Где |
|---|---|
| Принимает город, дату, тип мероприятия, категорию, бюджет; опционально длительность и язык | `search_contractors` |
| Жёстко отсекает занятых на дату, не берущих формат, не проходящих по бюджету, языку и часам | `_reasons` |
| Ранжирует детерминированно по фиксированным весам; при равном счёте — дешевле, шире по языкам, уже специализация, и лишь затем id | `_score`, `WEIGHTS` |
| Возвращает до 3 карточек с посчитанными фактами совпадения | `search_contractors` |
| Даёт дословную цитату из описания подрядчика как доказательство | `_quote` |
| Называет, чем кандидат отличается от соседей по выдаче | `_standouts` |
| Показывает занятость категории на выбранную дату | `availability_note` |
| Показывает всех отсеянных со всеми причинами сразу | `rejected` |
| Различает три исхода: подобрали / категории в городе нет / никто не проходит | `outcome` |
| Объясняет, что изменить в запросе, чтобы результат появился — только если это реально добавит кандидатов | `diagnose_request`, `suggestions` |
| Объясняет бедную выдачу сезоном, а не сбоем | `season_note` |
| Помечает синтетические профили и проставленные при подготовке цены и города | `flags` |
| Работает без ключей: отбор, порядок и диагностика не зависят от модели | `LLM_MOCK` |

## Что решение не делает — сознательно

Пункт «Что не входит» в ТЗ.

- **Бронирование, заявки, уведомления подрядчику.** Только рекомендация. Механизм
  подтверждения человеком в шаблоне есть, но в этой Задаче не задействован: изобретать
  действие ради демонстрации механизма значило бы нарушить ТЗ.
- **Дообучение модели на 66 записях.** За день это даёт пересказ датасета.
- **Расширение каталога.** Задача — помочь выбрать из списка, а не удлинить список.
- **Полировка интерфейса в ущерб объяснениям.** ТЗ расставило приоритеты явно.
- **Подбор сразу по нескольким категориям.** Категория — обязательный вход по ТЗ.
  Как направление развития описано в README, в решение не входит.

## Известные ограничения

Заявлены честно, чтобы эксперт не тратил время на их поиск.

- **Релевантность описания считается лексически**, по пересечению основ слов,
  а не эмбеддингами. Эмбеддинги ТЗ разрешает, но они требуют сетевого вызова, а
  детерминированный отбор без ключей нам дороже: проверяющий видит настоящее
  ранжирование даже без `.env`. Переход на эмбеддинги — направление развития.
- **Каталог кэшируется при первом обращении.** Если править CSV на живом сервере,
  нужен перезапуск бэкенда.
- **Окно занятости — 100 дней** из датасета, дальше данных нет.
- **Веса скоринга подобраны вручную** и зафиксированы в `WEIGHTS`. Они опубликованы
  в коде именно потому, что от них зависит порядок: менять их значит менять выдачу.
- SQLite, фоновые потоки вместо очереди, нет авторизации, CORS открыт — конфигурация
  для демонстрации, перечислена в README.
