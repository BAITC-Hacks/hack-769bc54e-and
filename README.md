## Описание решения и его назначение

<Одна фраза: кому, что и вместо чего.>

<2–3 предложения: какую проблему решаем, кто пользователь, что он получает на выходе.>

Решение построено как **агент**, а не как чат-бот: модель в цикле сама выбирает
инструмент, читает результат и решает, что делать дальше. Каждый шаг виден
пользователю в журнале, а перед действием, которое меняет внешнюю систему,
агент останавливается и ждёт подтверждения человека.

## Описание архитектуры

```
задача + материал ──> LLM ──> выбирает инструмент ──> результат ──┐
                       ^                                          │
                       └──────────────────────────────────────────┘
      действие меняет внешнюю систему? -> пауза -> человек: разрешить / отклонить
      инструменты больше не нужны -> итоговый отчёт
```

| Слой | Где | За что отвечает |
|---|---|---|
| Цикл агента | `backend/agent/core/loop.py` | шаг за шагом ведёт запуск, ставит на паузу, продолжает |
| Доступ к модели | `backend/agent/core/llm.py` | единственное место вызова LLM; здесь же mock-режим |
| Реестр инструментов | `backend/agent/core/tools.py` | регистрация, JSON-схемы, безопасный вызов |
| **Предметная область** | `backend/agent/core/domains/<домен>.py` | инструменты, промпт и примеры конкретной Задачи |
| Системный промпт | `backend/agent/core/prompts.py` | общая часть + `BRIEF` активного домена |
| HTTP API | `backend/agent/views.py`, `urls.py` | JSON-эндпоинты под `/api/` |
| Интерфейс | `frontend/app/`, `frontend/components/` | журнал шагов и запрос подтверждения |
| Команды разработки | `scripts/dev.py`, `scripts/verify.py`, `scripts/check_llm.py` | установка, запуск, тесты, сквозная проверка, проверка провайдера |
| Прогон качества | `backend/agent/evals/` | набор кейсов и таблица результатов в `docs/EVAL.md` |

Состояние запуска целиком лежит в БД (`Run.messages`, `Run.pending`), поэтому
запуск можно поставить на паузу ради человека и продолжить позже.
Ядро не знает о предметной области: смена Задачи = новый файл в `core/domains/`
и одна строка в `.env`.

### API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | режим работы, модель, активный домен |
| GET | `/api/samples` | примеры материала из активного домена |
| POST | `/api/runs` `{task, input}` | запустить агента |
| GET | `/api/runs/<id>` | статус и все шаги (интерфейс опрашивает раз в секунду) |
| POST | `/api/runs/<id>/approve` `{approve: bool}` | решение человека |

Контракт продублирован в `frontend/lib/types.ts` — при изменении `views.py` правится в том же коммите.

- **Frontend:** Next.js 16 (App Router), React 19, TypeScript в режиме `strict`, без UI-библиотек.

## Инструкции по установке

### Вариант 1 (рекомендуемый) — Docker

```bash
git clone <URL репозитория>
cd <папка>
docker compose up --build
```

Файл `.env` не нужен: без ключа приложение поднимается в mock-режиме (см. «Параметры окружения»).

### Вариант 2 — локально

```bash
git clone <URL репозитория>
cd <папка>
python scripts/dev.py setup      # или, если есть make: make setup
```

Создаёт `.env` из `.env.example`, ставит виртуальное окружение и зависимости бэкенда,
применяет миграции и ставит зависимости фронтенда. `scripts/dev.py` использует только
стандартную библиотеку и работает на Windows, macOS и Linux — `make` ставить не нужно.

То же самое вручную:

```bash
cp .env.example .env
python -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt   # Windows: backend/.venv/Scripts/python.exe
backend/.venv/bin/python backend/manage.py migrate
cd frontend && npm install
```

### Если порт занят

`bind: address already in use` на 3000 или 8000 означает, что порт держит другой процесс,
а не что проект сломан. Найти и освободить:

```bash
# Linux / macOS
lsof -ti tcp:3000 | xargs kill
```

```powershell
# Windows PowerShell
Get-NetTCPConnection -LocalPort 3000 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

Либо запустить на других портах: `docker compose up` с `ports: ["3001:3000"]`, тогда
`NEXT_PUBLIC_API_URL` должен указывать на фактический адрес бэкенда.

## Параметры окружения

Все параметры задаются в `.env` в корне (шаблон — `.env.example`). Переменные не обязательны:
без `.env` используются значения по умолчанию.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AGENT_DOMAIN` | `example` | имя модуля предметной области из `backend/agent/core/domains/` |
| `OPENAI_API_KEY` | пусто | ключ провайдера. Пусто → автоматически включается mock-режим |
| `OPENAI_BASE_URL` | пусто | пусто = api.openai.com. Любой OpenAI-совместимый endpoint |
| `OPENAI_MODEL` | пусто | модель **с поддержкой tool calling**. Пусто → mock-режим |
| `LLM_MOCK` | `0` | `1` — заскриптованная «модель» без сети. Включается сам, если пуст `OPENAI_API_KEY` или `OPENAI_MODEL` |
| `AGENT_MAX_STEPS` | `12` | предел вызовов модели за один запуск |
| `DJANGO_SECRET_KEY` | `dev-only-change-me` | ключ Django |
| `DJANGO_DEBUG` | `1` | режим отладки |
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` | адрес API для фронтенда |

**Проверка без наших учётных записей (п. 5.6.6 Положения).** При пустом `OPENAI_API_KEY`
приложение работает в mock-режиме: настоящая модель заменена заскриптованным сценарием,
но цикл агента, вызовы инструментов, пауза на подтверждение человека, журнал и отчёт —
настоящие. Личные аккаунты и платные подписки участников для проверки не требуются.
Чтобы увидеть работу с настоящей моделью, впишите в `.env` `OPENAI_API_KEY` и `OPENAI_MODEL`,
поставьте `LLM_MOCK=0` и перезапустите бэкенд. Перед этим стоит проверить провайдера:

```bash
python scripts/dev.py llm
```

Команда покажет endpoint, список доступных моделей и сделает один пробный вызов с
tool calling — именно на нём держится агент, и поддерживают его не все модели.
Смена провайдера — одна строка `OPENAI_BASE_URL`, код не меняется.

## Порядок проверки основного сценария работы

### Автоматически

При запущенном приложении:

```bash
python scripts/verify.py            # или: python scripts/dev.py verify
```

Скрипт (только стандартная библиотека Python) проходит весь путь: `/api/health` →
примеры → запуск агента → подтверждение действия → готовый отчёт. Печатает `OK` и
возвращает код 0, если сценарий пройден.

Ожидаемый вывод:

```
health      ok    домен=example mock=True модель=gpt-5.5
samples     ok    2 шт., берём «Выгрузка записей (CSV)»
run         ok    id=...
approval    ok    агент остановился на «notify_owner», подтверждаем
report      ok    шагов: 11 (thought, tool_call, tool_result, approval, final)

OK: основной сценарий пройден
```

### Вручную, в браузере

1. Открыть http://localhost:3000.
2. Нажать пример **«Выгрузка записей (CSV)»** — поля задачи и материала заполнятся.
3. Нажать **«Запустить агента»**.
4. В журнале справа появляются шаги: рассуждение → вызов инструмента → результат.
   Агент сам решает, какой инструмент вызвать следующим.
5. Дойдя до действия, меняющего внешнюю систему, агент **останавливается** и просит
   подтверждения. Нажать **«Разрешить»** (кнопка «Отклонить» тоже рабочая — агент
   учтёт отказ и не будет повторять действие).
6. В конце появляется итоговый отчёт: итог, доказательства, что сделано, что дальше.

Ожидаемое время прохождения — менее минуты.

### Тесты

```bash
python scripts/dev.py check     # тесты Django + tsc --noEmit
python scripts/dev.py eval      # прогон кейсов, отчёт в docs/EVAL.md
```

`docs/EVAL.md` — таблица «кейс / прошёл / вызовов модели / замечания» по набору из
`backend/agent/evals/cases.json`. Она показывает качество решения на наборе примеров,
а не на одном удачном прогоне.

## Известные упрощения

Заявлены честно, чтобы эксперт не тратил время на их поиск:

- фоновые потоки вместо очереди задач (для продакшена — Celery/RQ, интерфейс тот же);
- SQLite вместо полноценной СУБД;
- нет авторизации, CORS открыт, `ALLOWED_HOSTS = ["*"]` — конфигурация для демонстрации;
- инструмент `notify_owner` симулирует отправку, реальной интеграции нет;
- справочник в `domains/example.py` — плейсхолдер, а не данные заказчика.
